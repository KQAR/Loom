# AppFeature — what must stay true of the human surfaces

[`DESIGN.md`](../../DESIGN.md) says what these surfaces look like and
[`INTERACTION.md`](../../INTERACTION.md) says who operates them. This file is the working list of
invariants a change to the console, the request table or the inspector must not break — the ones
that were bugs first, and that neither spec states because they are about *this* implementation.

The rule underneath most of them: **the engine has a second writer.** An agent can change the same
state through MCP while a view is on screen, so a fact the engine owns is read from `status`, never
mirrored into a stored property that nothing reconciles ([root § Known Issues](../../AGENTS.md#known-issues) has what that cost when `isRecording` was a local flag).

**A child's delegates are one nested `switch` in the parent, never a case each.** The parent's reducer ends in a catch-all listing every child (`case .binding, .setup, .rules, …, .capture: return .none`), so a per-delegate case sitting in front of it means a delegate nobody wrote a case for compiles, runs and is dropped silently. `CaptureFeature.Delegate.ignoreHost` lived there: an action, a delegate case, and a doc comment saying the parent routed it to the engine — with no case, no sender in any view, and no test. Matching `case let .capture(.delegate(delegate))` once and switching inside makes the compiler require a case per delegate. It was deleted rather than wired, because "stop capturing this host" is already `RuleActions.dropFromCapture` and a second write path to one outcome is what this codebase does not do.

## The SSL scope's human surfaces

The whitelist decision is in the root [`AGENTS.md` § Known Issues](../../AGENTS.md#known-issues);
the engine's half is in
[`Engine/ProxyCore/CLAUDE.md`](../../Engine/ProxyCore/CLAUDE.md#the-ssl-scope-and-the-capture-drop-stage).

- **The request table shows relayed connections too** — `observeTunnels` is on for the app, still off in the engine default. Its **SSL** column has `lock.open.fill` for decrypted, `lock.trianglebadge.exclamationmark` for failed decryption, `lock.fill` for deliberate relay and `lock.slash` for plaintext. `FlowEncryption` reads the typed tunnel diagnostic (legacy CONNECT rows project into it), never error prose. The column matches App width (36pt): four states of one symbol are not guessable from the glyph.

- **CONNECT stays visible without owning the list.** `All Flows` is the raw sequence; Requests / Connections are one composable record-kind dimension, so Connections + Errors + host is one filter rather than a second store. Their counts come from engine aggregates over retained history; the Connections strip labels them capture-wide and never scans the 20k window.

- **The console is configuration-only.** It reports unexpected unread scope state, not failed-handshake counts or warning tint; per-connection failures and their Pass Through repair live on the request-table row, while MCP gets the retained aggregate.

- **Mixed TLS evidence stays mixed.** One success cannot prove every client/stack recovered. The aggregate reports `stillFailing` for failures only, `mixed` once both outcomes exist, and `latestResult` separately; `clearFlows` is the explicit evidence reset.

- **The card is the whitelist and one control that adds to it, nothing else.** Both lists are open, in the order the scope reads them (`Decrypting`, then the `Passed through` holes punched in it), with the add control under both — it writes to whichever one its picker names, so under just one of them it would read as belonging to that one. One surface per question: the table lists origins, the card holds the configuration.

- **The main window's answer is a row's context menu, not a surface of its own.** A CONNECT row holds `Copy Host` and exactly one scope item — no Replay and no rule, there being no exchange to stamp one from — and *which* item is the whole difference between the two kinds wearing the same lock: a *relayed* tunnel is a host nobody named, so Decrypt is the point of the row; a *failed* one is a host Loom is already trying to decrypt, so passing it through is the repair. Neither is read off the row: `RequestTable.Coordinator.scopeItems` asks the scope, and `offersDecrypt`/`offersExclude` split on the same `shouldIntercept`, so they are complementary by construction. Two gates, both bugs first: **the exchange must be TLS**, and **the scope decides the direction, never the scheme**. The wildcard widens by exactly one label (`parentWildcard`). Both directions travel up as `CaptureFeature.Delegate` cases to `SetupFeature` (`decryptHost` → `interceptHostTapped`, `excludeHost` → `excludeHostTapped`), so the table and the console card cannot drift on what either one means.

## Known issues (surfaces)

- **`MainView` uses a plain `HStack` deliberately — never `NavigationSplitView`, and no longer `HSplitView`.** *(verified 0.0.24.)* `NavigationSplitView` pays a quadratic AppKit KVO teardown on a sidebar category switch with live traffic: measured **8.7–16 s of main thread vs 143–224 ms** (61×) on the same view. `HSplitView` went too — a bare `NSSplitView` has no collapse semantics, so the sidebar could only be inserted and removed, which pops. The collapse now animates the pane's **width** (300↔0, trailing-aligned + `.clipped()`); the toolbar `sidebar.left` button and ⌃⌘S share one animated action. Three measured dead ends are recorded so they aren't re-walked (the `NSSplitViewController` bridge, centring the status chip on the content pane, removing the macOS 26 scroll-edge band): [`docs/decisions/navigation-split-view.md`](../../docs/decisions/navigation-split-view.md); the full `NavigationSplitView` investigation is [`docs/decisions/navigation-split-view-kvo.md`](../../docs/decisions/navigation-split-view-kvo.md). [DESIGN.md § main-window](../../DESIGN.md#layout-main-window) records the container decision.

- **The app renders in the pre-26 system design on purpose (`UIDesignRequiresCompatibility`), and that key has an expiry date.** DESIGN.md's baseline is macOS 14 controls (`.bordered`/`.borderedProminent`, never `.glass`) and every view in the tree is drawn that way — but macOS 26 layers on *system* chrome with no per-view opt-out: the shared-glass toolbar capsule (which stretches by however much a `.principal` item is padded) and the `NSScrollPocket` band across the window top (which survives `titlebarAppearsTransparent`, hiding the titlebar backdrop, and SwiftUI's `scrollEdgeEffectHidden`; AppKit's `NSScrollEdgeEffectStyle` is 26.1 and settable only on split-view/titlebar *accessory* controllers). `"UIDesignRequiresCompatibility": true` in the app's `infoPlist` (`Project.swift`) is the one lever that removes both. **It is honored by AppKit, not just UIKit** — measured on 26.5 with one probe binary and two Info.plists: `NSButton` 37×24 → 47×32, `NSTextField` height 24 → 21, titlebar 32 → 28pt. System control metrics move with it; Loom's own do not (sidebar 300, `LoomTheme` spacing, the 7pt capture dot), and no view is tuned to either design. Two consequences to hold onto: Apple documents the key as **temporary** and intends to drop it after Xcode 26, so when the glass chrome reappears it is a DESIGN.md decision to re-make (adopt it deliberately, per surface), *not* a build regression — and while the key works, the per-view dead ends recorded in `MainView.body` are dead for a reason, so don't re-walk them.

- **A custom SF Symbol can compile clean and still be `nil` at runtime.** *(verified 0.0.24 — `check.py` passes.)* `actool` succeeds, `Assets.car` is complete, the app builds, `Image(_:)` has no compile-time check — and the menu-bar icon is silently gone, because CoreUI refused to decode the symbol. Cause: it subdivides arcs into Béziers by radius, so variants drawn at different stroke weights get different segment counts and the weight interpolation has no point correspondence. `Tools/symbol-template/build.py` flattens every arc to a fixed chord count to avoid it, and **`check.py` is the pass condition** — now run by the CI build job (before the build, so a broken mark fails in seconds), not just by hand — it compiles the catalog and asks a real bundle for each symbol back. See [DESIGN.md § Brand mark](../../DESIGN.md#brand-mark).

- **HTTPS interception works (M2); one-click *user-domain* CA trust is wired and shipping.** With SSL on and a host in scope, Loom MITM-decrypts and captures HTTPS. Apple domains legitimately fail (cert pinning) — expected, not a bug. A client only trusts the leaf if Loom's root CA is trusted. Three ways, in order of what's actually available:
  - **One-click (user-domain) — works today, no helper, no Developer ID.** The panel's **"Install & Trust"** button (`SetupFeature.installAndTrustCATapped` → `CertificateTrust.installUserTrust`) adds the CA to the login keychain and sets user-domain trust via Authorization Services — one login-password prompt. Safari and apps using the system trust evaluation then accept Loom's leaf. This covers the common single-user case; it's the default path a user should take.
  - **Manual (system-domain).** The panel also shows a copyable `sudo security add-trusted-cert -d -r trustRoot -k /Library/Keychains/System.keychain <path>` (get the path from `export_ca_certificate`) for machine-wide trust.
  - **Privileged helper (system-domain) — deliberately not the CA-trust path (0.0.17).** A root helper ships (next entry, and [§ Scope](../../AGENTS.md#scope) 0.0.17) and does **not** install CA trust: under an ad-hoc signature the caller check is `identifier "com.loom.app"` alone, which any local process can forge, so the helper's surface is limited to what an admin account can already do silently (`networksetup`) or whose worst case is a reversible local DoS (the pf QUIC block). A root daemon that installs a trusted root CA, reachable by anything on the machine, is machine-wide MITM — that needs a non-forgeable signature, i.e. the Developer ID certificate the Sparkle entry declines to buy. What the old version of this entry got wrong ("a root daemon can never load", from two refusals that had never been run) is in [`docs/decisions/privileged-helper.md`](../../docs/decisions/privileged-helper.md). User-domain trust above remains the shipping path.

## Performance — what the window pays for

The framing is the root's: **performance is a hard requirement, not a nice-to-have.** A capture
proxy routinely holds tens of thousands of flows with multi-MB bodies, and every list and every
large-data render must stay smooth at that scale. These are the measured rules for the surfaces;
the store's half is
[`Engine/ProxyCore/CLAUDE.md`](../../Engine/ProxyCore/CLAUDE.md#performance--what-the-store-pays-for).

- **Never render a large/unbounded collection eagerly.** Row-based views use a lazy container — `List`, `Table` (both NSTableView-backed), or `LazyVStack`/`LazyVGrid` in a `ScrollView`. Never `ScrollView { VStack/ForEach over data } }` for a collection that can grow (only for a fixed, small set of blocks). **`Table` is lazy about row bodies and not about its collection**, which is why the request list owns an `NSTableView` directly (`RequestTable`): measured, `Table` evaluates 32 row bodies whether the data is 2 000 rows or 100 000, but walks the whole collection — reading every element and every `id` — about **five times per data change** (100 006 subscripts for 20 001 rows, 70–120 ms). At a capture batch every 100 ms that is the main thread, and it makes a paged data source impossible by construction.

- **Update a table by diffing it, never by reloading it.** `reloadData()` discards every realized cell to rebuild identical content: measured on a 2 000-row table applying one capture batch, **380 ms reload vs 42 ms diffed**, and the diffed path stays flat as the capture grows (46 ms at 20 000 rows) because it costs the viewport rather than the capture. Three rules hold that up: the diff computes **structure only** (a head trim and a tail append); content correctness comes from refreshing the **visible** rows; and a cell re-hosts its SwiftUI content only when a **draw-relevant** comparison says it moved, because assigning `rootView` runs an update transaction whether or not the value changed. **Nothing else in the update may walk the row set either** — the selection sync asks the *table* where its selection is (O(1), correct because `NSTableView` shifts its own index across the `removeRows`/`insertRows` that already ran), keeping a scan only for a `.reload` or a selection the store moved. `RequestTableSelectionTests` pins the **overhead ratio** at ≤1.5×, not a time. Why each of those was measured rather than assumed: [`docs/decisions/capture-path-performance.md`](../../docs/decisions/capture-path-performance.md).

- **The tail-follow is a glide, and it yields to the reader.** Row-edit animations are gone; the motion belongs to the scroll — a display link closes a fixed fraction of the *remaining* distance per unit time (`glideTimeConstant`), so a batch landing mid-glide moves the target instead of restarting the movement. Three rules, each of which was a bug: whether to follow is measured from the viewport's **geometry** a moment before the edit lands, **never from a flag** (a flag stays armed through momentum, scroller drags, keyboard scrolls and the table's own head-trim shift, and the list yanks itself down while someone is reading); an **in-flight glide counts as being at the bottom**; and **nothing programmatic touches the offset during a gesture** or for half a second after it, because the glide and a live scroll write the same clip view. What it looked like before: [`docs/decisions/capture-path-performance.md`](../../docs/decisions/capture-path-performance.md).

- **Build a batch on a local copy, then assign the observed property once.** A stored property of an `@ObservableState` value costs work proportional to what it holds on *every write*: on the 20 000-row flow list, one insert through the state is **690 µs** against **2.6 µs** into a plain `IdentifiedArray`, so mutating it once per flow made a batch quadratic — **14 s to fill the window against 90 ms** (`CaptureFeature.State.recordFlows`). It was invisible at the old 2 000-row cap and appeared the moment the cap moved: the shape was always wrong and only the size made it show. `fillingTheWindowIsLinear` guards it.

- **A projection read every render is cached, not recomputed.** `CaptureFeature.State.displayFlows` is O(n) in the window whenever a category or a needle is involved and is read on every render (twice — the empty-state probe reads it too). It is recomputed from a single funnel (`refreshVisibleFlows`) driven by `didSet` on the inputs, **not by call sites remembering**: a cached list whose staleness depends on every mutation site is a list that renders wrongly and silently, which is what the first version of this did. The sidebar's three grouping lists (`hosts`/`apps`/`devices`) are the same shape and were the last thing still sorting on read — 0.60 ms for the three, per render, against 0.001 ms off `refreshSidebarRows`. They became named row types (`HostRow`/`AppRow`/`DeviceRow`) on the way, because a tuple cannot be stored in `Equatable` state.

- **Caching it is not enough once the cache is rebuilt at capture rate.** With a category or a needle selected, refreshing that projection filters the whole window on **every capture batch** — at 20 000 rows, **7.9 ms for a host category and 8.9 ms for a needle against 1.8 ms unfiltered**, ten times a second, to re-derive a list that changed by the thirty rows the batch carried. `recordVisibleFlows` folds the batch in instead (1.7 ms and 3.2 ms), and the shape of it is the reusable part: it **returns false and lets the full rebuild happen** for every case it cannot prove, rather than approximating. All three declines are about *order*, because the projection follows the capture's insertion order and appending is only correct at the end — a shown row that stops matching, an unshown row that starts matching, and a display-cap trim. `VisibleProjectionTests` checks the fold against a from-scratch rebuild under each transition, which is the only honest guard for a second writer of a cached list. Two things it got wrong first, including a version that came out slower than the rebuild it replaced: [`docs/decisions/capture-path-performance.md`](../../docs/decisions/capture-path-performance.md).

- **A trim that fires every batch costs the window every batch.** `IdentifiedArray.removeFirst` shifts the backing storage and rebuilds the id index, so it costs the whole window however few rows it drops: at the 20 000-row cap a steady-state batch was **1.79 ms against 0.25 ms** below the cap, all of it this call, because trimming exactly to the cap leaves the next batch over again. `CaptureFeature.State.trimSlack` cuts to `displayCap - 500` instead — same 2.5 % trade as `FlowPersistence.pruneSlack` — and it cuts **below** the cap rather than drifting above it, which is the only direction available: a row past `FlowLimits.windowRows` is a row on screen whose flow no read can resolve (`FlowLimits.isOrdered`). The cost is one invariant, stated rather than quietly dropped — per-flow and batch recording no longer leave the same *number* of rows, because they cross the cap at different moments; what still holds, and what `batchRecording_matchesPerFlowRecording_atTheCap` pins, is that the two are suffixes of the same capture agreeing on every row they both hold.

- **Cheap row bodies.** No per-row allocation of expensive objects (date formatters, regexes, `JSONDecoder`, `URLComponents`) — hoist to a shared static or a direct scan. `Flow.host` goes through `URLHost` (an authority scan that defers to `URLComponents` only for percent-escaped / punycode / malformed URLs), and a host-filtered list compares via `URLHost.hostMatches` so it never materializes a host per row. Hand genuinely large text to AppKit (`NSTextView`), not a SwiftUI `Text`.
