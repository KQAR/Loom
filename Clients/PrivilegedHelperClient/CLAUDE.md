# The system-proxy subsystem — helper, `networksetup`, and pf

`PrivilegedHelperClient` is one entry point over **two paths**: the root LaunchDaemon when it is
installed and approved, and `networksetup` + one osascript prompt when it is not. The helper is a
latency-and-prompt optimisation, never a capability — nothing here may become unreachable because
it is absent.

Three things bound the whole surface, and they are decisions rather than gaps:

- **The XPC interface takes parameters, never a script**, and not the host either — the daemon
  hardcodes `127.0.0.1`, so this surface cannot redirect the machine's traffic.
- **Under an ad-hoc signature the caller check degrades to `identifier "com.loom.app"`**, which any
  local process can forge. So the helper only does what an admin account could already do silently,
  or whose worst case is a reversible local DoS.
- **CA trust is deliberately not on it.** A forgeable caller plus root CA installation is
  machine-wide MITM; that stays the user-domain button and the manual `sudo`. Reopening this needs
  a non-forgeable signature, i.e. the Developer ID certificate the Sparkle decision declines to buy.

**The version-stamp rule travels with these entries**: each carries the version it was last
*verified* in, and most of this subsystem cannot be verified cheaply — a real install, a real
approval in System Settings, a real pf ruleset. `scripts/verify-known-issues.sh` deliberately
cannot reach any of it. An entry that says "not re-verified since 0.0.17" is being honest, and
that is more useful than a stamp nobody could back; move a stamp only when you actually toggled it.

## Known issues (system-proxy)

- **A privileged helper is back (0.0.17), scoped to the system proxy.** *(the shape is verified 0.0.19 — the static framework, the embed step, the absence of CA trust are all in the tree; the three runtime rules below are **not re-verified since 0.0.17**, because each needs a real install, a real approval in System Settings and a real launchd record.)* `Helper/Shared` (`LoomHelperShared`: XPC protocol, service names, and `SystemProxyScripts` — the shell **both** ends run, because two copies is how a privileged path and an unprivileged one drift) and `Helper/Daemon` (`loom-helper`, a root LaunchDaemon embedded by `Scripts/embed-helper.sh` **before** the final CodeSign step so the app's seal covers both). `SystemProxyApplier.apply` tries the helper first and falls through to `networksetup` + osascript when it isn't installed *or doesn't answer* — a broken helper must not take the toggle down with it. Four rules, each of which cost a build to find:
  - **`LoomHelperShared` is a *static* framework.** A command-line tool carries no rpath into the app bundle, so as a dynamic framework the daemon died at launch on every spawn. It also means the privileged process loads no third-party code at runtime, which is the better shape anyway.
  - **`HelperInstall.ensureReady()` must never `unregister()`.** Replacing the app leaves launchd holding a job that names the old binary — it happens on every Sparkle update — and the repair is one idempotent, prompt-free `register()` after a 5-second liveness ping. The destructive version turned a helper that merely wasn't answering into one that was *gone*, spending the human's approval for nothing.
  - **`register()` throws while succeeding** on a first install (`Operation not permitted` *and* status `requiresApproval`). Read the status, not the throw. The approval switch lives in System Settings, so `helperState` is re-read on every refresh rather than cached.
  - **It does not touch CA trust** — see the CA-trust entry above for why the forgeable caller check bounds this surface.

- **System-proxy config works without the helper (one admin prompt when pf work rides along).** *(**not re-verified since 0.0.17.** Every claim here needs a real toggle on a real machine — an admin prompt, a pf ruleset, a `networksetup` write — so nothing in `verify-known-issues.sh` can reach it. Treat the details as last-measured-in-0.0.17 rather than as current.)* `SystemProxyApplier` runs `networksetup` directly first — silent for admin users — but success requires the script's **exit status** too, and the QUIC (pf) section always fails un-escalated because `/dev/pf` is root-only. So an enable escalates to one osascript admin prompt even for admins (that's where the pf work was always designed to run); a disable with no QUIC block to restore (`com.loom.quicBlocked` in UserDefaults says so) carries no pfctl and stays silent. Judging by proxy routing alone was the bug: admin users ran with the proxy set and QUIC never blocked while the panel claimed otherwise. A cancelled prompt after the proxy half landed reports an honest partial success naming what's missing. State is verified via `SCDynamicStoreCopyProxies`, synced into the UI at boot, and auto-disabled on quit (`AppDelegate.applicationShouldTerminate`) — the quit path is guarded on Loom still holding the setting, so it can't clear someone else's. A crash skips the quit cleanup; the boot sync surfaces the stale override on next launch, and `applicationDidFinishLaunching` clears an **orphaned** QUIC block (`quicBlocked` still set while the proxy no longer points at Loom) — without that there was no path in the UI to undo a machine-wide UDP/443 drop, because the toggle only ever runs the enable branch while the proxy is off. `SystemProxyApplier.apply` is serialized on a lock: the panel and the agent's `set_system_proxy` are independent writers and only the UI one is debounced, so overlapping runs used to trample each other's pf work files under `/var/root/com.loom`. **Since 0.0.17 the prompt is avoidable**: with the privileged helper installed and approved, `apply` routes the same script through it and nothing is asked. The un-escalated path above is unchanged and still the fallback — for a build with no helper, a helper the human hasn't approved, and a helper that doesn't answer. An agent can tell which it is going to get: `get_proxy_status` reports `privilegedHelper` and sets `systemProxyChangePrompts` when a `set_system_proxy` call would stop and wait for a human at the machine, which otherwise just looks like a hang.

- **Enabling the system proxy also blocks QUIC (`QUICBlocker`).** *(**not re-verified since 0.0.17** — same reason as the entry above: pf needs root and a live toggle.)* Browsers default to HTTP/3 over QUIC (UDP 443), which a TCP HTTP proxy can't intercept — so without this, browser page loads bypass Loom entirely (only TCP h1/h2 app traffic is captured). The system-proxy enable script appends a pf rule dropping outbound UDP 443, forcing browsers to TCP fallback; disable/quit restores it. Safety: it copies the user's `/etc/pf.conf` and appends a `com.loom.quic` anchor (never overwrites; an unreadable baseline **fails closed** — no synthesized conf, QUIC just stays unblocked, because `pfctl -f` replaces the whole loaded ruleset), records prior pf-enabled state in a marker file, and restore reloads the pristine ruleset. The pf fragments are shell functions whose **return status is the contract**: it becomes the script's exit status, which is how `SystemProxyApplier` knows the un-escalated run didn't do the pf work and must escalate (see the system-proxy entry above). pf needs root, so this rides the same osascript admin call as the proxy — **the live pfctl path is unit-tested + `pfctl -nf` syntax-validated but needs one real toggle to verify end-to-end** (like the other privileged paths). pf is macOS-specific: a named anchor is only evaluated because we append `anchor "com.loom.quic"` to the loaded main ruleset.

- **Loom is not the only app that sets the system proxy, and the state is watched live.** Charles / Proxyman / whistle set the same setting and only one wins. `SystemProxyMonitor` follows `SCDynamicStore`'s proxy key (no polling) and `SetupFeature.task` keeps the panel honest — before this, state was read only at boot / after Loom's own write / on quit, so another app taking over left the switch claiming "on" until the panel was reopened. The answer is three-valued (`SystemProxySnapshot.routing(loomPort:)` → `.loom` / `.off` / `.other(host:port:)`), **one definition** shared by the panel row, the quit decision and `get_proxy_status` (`"on"`/`"off"`/`"other"` + `systemProxyPointsAt`). `.loom` requires *both* HTTP and HTTPS: half-routed means every `https://` bypasses Loom, which is the empty-capture case this exists to explain. Snapshots are ignored while `systemProxyBusy` — the enable script writes one network service at a time, so mid-apply readings are genuinely half-applied — and `.systemProxyResult` re-reads once to settle.

- **Loom deliberately does not back up and restore the previous proxy owner.** Owner decision: restoring is only correct if that app is still running, and Loom cannot know — re-enabling a proxy pointed at an exited Charles would break every request on the machine, which is worse than leaving the setting off. So enabling Loom overwrites, disabling turns the proxy *off* (not back to Charles), and the surfacing above is the mitigation: the panel and the agent both name who holds it, and the human switches back themselves. `ProxyBackup` / `ProxyServiceState` used to exist in `HelperProtocol` and read like the missing half of this feature; they were the *daemon's* crash-watchdog bookkeeping, never this path, and they went with the daemon in 0.0.16. The decision above is unchanged and is not waiting on them.
