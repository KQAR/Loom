Changing traffic

Capturing is half of it. The other half is sending the request again with something different, or changing it before it ever leaves the machine.

Replay

Select a flow and replay it. You can override the method, the URL, headers (set or remove) and the body before it goes out. The result arrives as a new flow that remembers what it was replayed from, so you can compare the two.

Comparing is a first-class answer rather than a squint: Loom diffs status, headers — with repeats preserved — and bodies line by line, and says plainly when one side never answered. Timing is deliberately not counted as a difference, since two runs never share it.

Rules

A rule is a matcher plus an action, applied to live traffic. Open Rules in the sidebar, or flip them all off at once with the Rules switch in the console — the badge counts the active ones.

ActionWhat it does
MockAnswer locally with a status, headers and body you supply. The request never reaches the server.
Map remoteSend the request to a different host or path — production URL, staging server.
RewriteChange headers or body content on the way through, in either direction.
BlockFail the request, so you can see how the client copes.
DelayHold it for a while first — slow networks, race conditions.
Drop from captureLet it through untouched but never record it. This is the noise filter, not a way to affect the client.

Rules can be put in groups and switched as a set, which is how you keep one scenario ("everything mocked", "staging") a single toggle away from another.

A rule can also be scoped to where the traffic came from — one app, one device. Traffic Loom could not attribute does not match such a rule, on purpose: a scoped rule that fired on unknown origins would be worse than one that didn't fire.

A dropped exchange leaves no flow, so there is nothing in the table to show that the rule worked. The Rules panel counts the drops per rule instead — that counter is the only place an absence you asked for can be seen.

Breakpoints

A breakpoint holds a matching exchange mid-flight, before it goes upstream, and waits. Arm one from the Breakpoints panel; while anything is held, an orange row appears in the console so you can't forget about it.

From the window you have two decisions: let it proceed unmodified, or abort it. Editing a held request is done by an agent, over the control port — deliberately, so there is one write path onto a held connection rather than two.

Breakpoints are not saved across a relaunch, because a held exchange is a live connection someone is waiting on. A hold can also end on its own if the client hangs up or the watchdog fires.

HAR, in and out

A capture can be exported as HAR — optionally redacted — and a HAR from somewhere else can be imported and read in the same window, which is the usual way to look at a capture someone sent you.
