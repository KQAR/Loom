Decrypting HTTPS

Reading an HTTPS body takes two separate things: the client has to trust Loom's certificate, and you have to tell Loom which hosts to decrypt. Neither happens on its own.

1. Trust the certificate

Turn on the HTTPS switch. Loom generates its own certificate authority the first time and mints a certificate per host from it. Until that CA is trusted, the tile goes yellow and a card appears with an Install & Trust button — that is the whole step for this Mac.

For a phone or another machine, use the link in the Device tile's instructions and trust the downloaded certificate there. On iOS that is two places: install the profile, then enable it under Settings ▸ General ▸ About ▸ Certificate Trust Settings.

Loom's CA is generated on your machine and its private key never leaves it. Removing trust is done in Keychain Access, like any other certificate.

2. Name the hosts to decrypt

The SSL scope is a whitelist. It starts empty, and while it is empty Loom passes every HTTPS origin through untouched — encrypted end to end, exactly as if Loom weren't there.

Open SSL Scope in the console and add a host, or a glob:

api.example.com
*.example.com

From then on those hosts are decrypted and their requests and responses show full headers and bodies. Everything else stays relayed.

A relayed host records no flow at all. That is the one thing worth remembering about the whitelist: a host you haven't named looks exactly the same in the table as a client that never ran. If traffic seems to be missing, check the scope before you debug the client.

What Loom saw but couldn't read

Because that state is so easy to misread, Loom records every origin it relayed and why. The SSL Scope row shows the count, and expanding it lists the hosts with a reason each:

ReasonMeaning
Not in scopeYou haven't named it. One click away from being captured.
ExcludedAn exclude pattern covers it. You asked for this.
Interception offThe HTTPS switch is off entirely.

Adding a host from that list is the fastest way in: you are picking from what actually happened rather than guessing a hostname.

When a handshake fails

If the upstream server refuses the connection, the flow carries the error and names which side rejected whom, and the row shows it in the table. A server that requires a client certificate is the common case — see Client Certificates in the console, where you can add a PKCS#12 bundle scoped to a host pattern.

Some apps pin their certificates and will refuse Loom's no matter what you trust. That is the app working as designed; there is nothing to configure here.
