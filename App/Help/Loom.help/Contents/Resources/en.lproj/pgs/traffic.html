Getting traffic into Loom

Loom only sees what is sent to it. It listens on three ports, and which one a client can use depends on how much that client is willing to be told.

PortWhat it is
9090The HTTP/HTTPS proxy. This is the one you normally use.
9091A SOCKS5 listener, one port up, for clients that only speak SOCKS.
9092The control port an AI agent talks to. Loopback only — never LAN.

The whole machine at once

Turn on the System switch in the console. macOS routes every app that respects the system proxy through Loom, and turning it off restores nothing — it just switches the system proxy off again.

If another proxy (Charles, Proxyman, a VPN client) already holds the system proxy setting, enabling Loom's takes it over, and the console's alert line tells you whose it was. Loom cannot give it back later, because it has no way to know whether that app is still running.

Enabling the system proxy also blocks QUIC, so browsers fall back to HTTP/2 where Loom can see them. That part needs root, which is what the privileged helper is for — install it once and the toggle stops asking for a password.

One command

curl -x http://127.0.0.1:9090 https://example.com

Most tools take the same idea as environment variables:

export HTTP_PROXY=http://127.0.0.1:9090
export HTTPS_PROXY=http://127.0.0.1:9090

A phone or another machine on the same Wi-Fi

Click the Device tile in the console. It shows a QR code and the instructions for the device: set a manual HTTP proxy to this Mac's LAN address on port 9090, then open the certificate link to trust Loom's CA. The tile counts the devices currently connected.

Loom binds 0.0.0.0 while device capture is on, so the address in the console header changes from 127.0.0.1 to the LAN one. Traffic from a device is grouped under it in the sidebar, with the apps Loom could name nested underneath.

Clients that only understand SOCKS

Point them at socks5://127.0.0.1:9091 — the usual case is a tool that reads ALL_PROXY but not HTTP_PROXY, or a GUI with only a SOCKS field. Loom works out what the traffic actually is by looking at the first bytes, not at the port, so HTTPS and WebSocket over SOCKS are captured the same as over 9090.

Clients that ignore proxy settings entirely

Some runtimes never look at the environment at all — Node's global fetch is the common one. For those, create a reverse-proxy endpoint: a local port that stands in for one upstream origin.

Open Reverse Proxies in the console, add the upstream (https://api.example.com), and point the client at the local port Loom gives you.

  • The local hop is plain HTTP even when the upstream is HTTPS, so the client needs no certificate and no keychain step.
  • The captured flow records the real upstream URL, not 127.0.0.1:port — so rules and searches written against the real host keep matching.
  • Endpoints survive a relaunch, because the port is usually written into some config file that Loom restarting doesn't edit.

One thing Loom deliberately cannot do: capture a process that ignores every proxy setting and can't be given a reverse-proxy endpoint. That would need transparent redirection at the packet layer, which Loom does not do.
