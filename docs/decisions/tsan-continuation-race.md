# The ThreadSanitizer report that isn't Loom's

> Moved out of `AGENTS.md` on 2026-08-07 (0.0.18), unedited. It is a **record**, not
> an instruction: what was tried, what it cost, and why the current shape is the
> shape. The invariant it produced lives in [`AGENTS.md` § Known Issues](../../AGENTS.md#known-issues), which links
> here — read that first; come here when you are about to re-open the question.

**The `Thread Sanitizer (ProxyCore)` job is intermittently red on a report that is not Loom's — upstream, `swiftlang/swift#57803`.** The signature is always the same: a write in `withUnsafeThrowingContinuation`'s suspend/resume glue against a read in `UnsafeContinuation.resume(returning:)` inside `NIOCore.EventLoopFuture.get()`, followed (probabilistically) by an `abort()` attributed to whichever test was running. **A Loom symbol can appear and still not be the bug, and that is the part this entry used to get wrong.** It said every racing frame belongs to NIOCore or the Swift runtime; during the Swift 6 migration two reports had `LoomProxyCore.ProxyEngine.startReverseProxies()` as frame #0 of the *write* side. That is not Loom touching shared state — it is the async frame that suspended across `EventLoopFuture.get()`, and the address is its coroutine context ("heap block … allocated by `runJobInEstablishedExecutorContext`"), written by the runtime's suspend glue. The discriminator is therefore **not** "does a Loom name appear" but **does Loom code perform the access**: a Loom frame at the top of a stack whose remaining frames are all NIOCore/NIOPosix/runtime is the awaiting function, and the one that shows up is simply whichever `EventLoopFuture.get()` bridge the suite hits most (`startReverseProxies` runs on every engine start). A report naming a Loom symbol *below* the top, or with a Loom frame on both sides, is a different animal — that one is ours. `Tools/tsan-continuation-repro/` reproduces the upstream shape in ten lines with no NIO and no Loom code, which is the same reproducer as the upstream issue (closed in 2023 as no longer reproducing; this sighting is macOS 26 with the current toolchain). Measured with `.github/workflows/tsan-reverse-proxy-hunt.yml` (dispatch-only, `suite`/`skip`/`iterations`): it reproduces with the suite that first exposed it **excluded entirely**, and the rate tracks how many engines — hence how many `EventLoopFuture.get()` bridges — one process runs, not which tests are selected. It first went red on main at `92da1f0` because the reverse-proxy round added 19 more engine-building tests, not because that code is wrong.

**It is suppressed now, not re-run.** Re-running stopped clearing it — three reds in a row across #229 and #230, the last two on a diff that changed two version-number strings — which retires the old inference in this entry ("CI stopped caching build products, so every run compiles the world on a busier machine"; it was flagged as unmeasured, and this is the retirement it asked for). `Tools/tsan/suppressions.txt` holds one entry, loaded by both TSan workflows, and the file argues its own breadth. Four things about it are load-bearing:

- **The channel is `TEST_RUNNER_TSAN_OPTIONS` as an *environment variable* of `xcodebuild`,** and the two wrong forms both failed **silently** — no error, an unprotected run that reads exactly like a clean one. `env: TSAN_OPTIONS` never reaches the test process (xcodebuild launches `xctest` with a scrubbed environment); the same name passed as a *build setting* reaches only the build environment. `__tsan_default_suppressions()` compiled into the test target is not an option either: TSan reads suppressions during its own init, before the test bundle loads, and the host executable is Apple's `xctest`.
- **The pattern has to be whole-stack `race:`, not `race_top:`.** `race_top:` was the design — match only the frame performing the access, so nothing broader than the glue could ever be hidden — and it does not work: with both `race_top:` entries loaded *and parsed* (the log prints each parsed entry), the report went through unsuppressed, including on a run whose write-side top frame was that very glue. Only `race:UnsafeContinuation.resume` matched.
- **That breadth is checked, not asserted.** `UnsafeContinuation.resume` is a frame only when the racy access happens *inside* `resume` — a coroutine-frame access — so async code racing on its own state is still reported. `Tools/tsan-canary/` proves it: two deliberate races (plain pthreads, and four `Task`s read-modify-writing a class property while continuations resume cross-thread), both of which must still be reported or the canary job fails. The `async` mode is the shape of the three real defects below.
- **A suppressed report is still counted.** `print_suppressions=1` plus a `::notice::` in the Report races step keeps the flake's frequency visible instead of turning it into silence, and the job warns when a run shows neither a report nor a suppression match — that silence is either a clean run or the channel having broken again, and the log cannot tell them apart.

One log-reading trap while you are in there: `xcodebuild`'s tail line says `Executed 0 tests` for this bundle and prints `** TEST SUCCEEDED **`. It counts XCTest cases and there are none — the suite is Swift Testing. Count `Test …() passed after` lines (the hunt workflow's summary does) or read the result bundle; do not read that line as a run that never happened.

**So a red TSan job now means something.** Read the report: check whether Loom code performs the racing access, not merely whether a Loom name appears. Three real defects were found while chasing this and none of them were it: a detached-`Task` test teardown that ran during the *next* test, `ReverseProxyServer.stopAll()` iterating `channels.keys` while `stop(id:)` removed from it (undefined behaviour on every engine stop), and `ProxyEngine` never shutting down its `MultiThreadedEventLoopGroup` (two leaked threads per engine — a real defect for an embedder, since `LoomProxyCore`'s engine is not a singleton; `shutdown()` is the terminal teardown that reclaims them).

**What the job's scope costs, and it is not hypothetical (0.0.16).** `-scheme ProxyCoreTests` means every *other* bundle is structurally exempt from this check — and the same defect class was sitting in one of them the whole time. `MCPServer` allocated its own `MultiThreadedEventLoopGroup` at `init` with no shutdown path at all (`stop()` closed the channel only), and all 26 of its real-server tests used the exact `defer { Task { await server.stop() } }` that `EngineTeardown.swift` exists to document. `MCPServer.shutdown()` and `Engine/MCPServer/Tests/ServerTeardown.swift` are the fix. The transferable part: a scoped job (like a suppression) hides a *category*, not just an instance — so when this entry's advice gets applied, apply it to the bundles the job does not run. The same sweep found 19 tests inside `ProxyCoreTests` building a `ProxyEngine` and never tearing it down, because `group` is a `let` allocated at `init` and never calling `.start()` does not make it free. That is precisely the "the rate tracks how many engines one process runs" mechanism above, being paid for nothing.
