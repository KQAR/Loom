# The privileged helper: two attempts, and seven things that each cost a build

> Moved out of `AGENTS.md` on 2026-08-07 (0.0.18), unedited. It is a **record**, not
> an instruction: what was tried, what it cost, and why the current shape is the
> shape. The invariant it produced lives in [`AGENTS.md` § Known Issues](../../AGENTS.md#known-issues), which links
> here — read that first; come here when you are about to re-open the question.

**A privileged helper is back (0.0.17), scoped to the system proxy — and the story of the one deleted in 0.0.16 is why this entry is long.** `Helper/Shared` (`LoomHelperShared`: XPC protocol, service names, and `SystemProxyScripts` — the shell **both** ends run, because two copies is how a privileged path and an unprivileged one drift) and `Helper/Daemon` (`loom-helper`, a root LaunchDaemon embedded at `Contents/Library/HelperTools/com.loom.proxyhelper` with its plist at `Contents/Library/LaunchDaemons/`, copied in by `Scripts/embed-helper.sh` **before** the final CodeSign step so the app's seal covers both). `SystemProxyApplier.apply` tries the helper first and falls through to the existing `networksetup` + osascript path when it isn't installed *or doesn't answer* — a broken helper must not take the toggle down with it. What it buys: enabling the system proxy no longer costs an admin password every time, because the pf (QUIC) half needs root on an admin account too. Seven things that each cost a build to find, and the last three are the expensive ones: the tool product is named `loom_helper` unless `PRODUCT_NAME` says otherwise (Xcode sanitizes, as with `loom-mcp`) and the plist's `BundleProgram` names the file on disk; a command-line tool has no Info.plist, so without `CREATE_INFOPLIST_SECTION_IN_BINARY` + `PRODUCT_BUNDLE_IDENTIFIER` it signs as `loom-helper-<hash>` and the app's check on the daemon (`identifier "com.loom.proxyhelper"`) can never pass; `register()` **throws while succeeding** on a first install (`Operation not permitted` *and* status `requiresApproval` — read the status, not the throw); and the approval switch lives in System Settings, so `helperState` is re-read on every refresh rather than cached.

**Fifth: the daemon must not link anything from the bundle.** As a dynamic framework, `LoomHelperShared` was resolved by `@rpath`, and a command-line tool carries no rpath into the app bundle — dyld failed, the daemon died at launch, launchd logged `EX_CONFIG` and respawned it on a ten-second loop (179 times), and from the app's side the XPC call simply never answered: no reply, no error, no process. `LoomHelperShared` is a **static** framework for this reason, which also means the privileged process loads no third-party code at runtime. An `@executable_path/../Frameworks` rpath would have worked and is the worse shape.

**Sixth, and it will happen to every user on every update**: replacing the app leaves launchd holding a job that names the *old* binary. It refuses to start it, `SMAppService.status` still reports `enabled`, and the XPC call then neither replies nor errors — it hangs to the timeout, so the console row spins for a minute and then silently falls back to the password prompt. Reproduced by one rebuild; a Sparkle update is the same event. `HelperInstall.ensureReady()` is the fix and the gate: a 5-second `helperVersion` ping (a liveness probe must never inherit the operation's long timeout), and on silence one idempotent, prompt-free `register()` to re-point the job at the current bundle, then one more ping — result cached per launch. **That path must never `unregister()`**, and this was learned by shipping the mistake into the live loop: the destructive version turned a helper that merely wasn't answering into one that was *gone*, spending the human's approval for nothing. Dropping the record is a repair, and a repair is something the human asks for on the console row — where it also waits for the removal to be visible before re-registering, because `unregister()` returns before it lands and the race leaves BTM at `[disabled, allowed]`. When even that fails the state is `unresponsive`, surfaced as an orange **repair** row rather than as `on`, because "approved but silent" and "never installed" need different words.

**Seventh: a launchd label is a machine-wide namespace, and a poisoned record cannot be repaired from inside the app.** After a `rm -rf DerivedData` replaced the app bundle at the same path, launchd kept resolving the *old* one — `Could not find and/or execute program specified by service: 3: No such process` — while `SMAppService.status` reported `enabled` and `register()` reported success. Reinstalling into `/Applications` did not help either, because a differently-signed `Loom.app` had once lived at that path and the record carried its launch constraint (`properties = … needs LWCR update | has LWCR`, every spawn refused with `EX_CONFIG`). What fixed it was a **fresh label** (`com.loom.helper` → `com.loom.proxyhelper`); with that, the ad-hoc daemon registered, launched as uid 0 and served both toggles on the first try. Two lessons: **ad-hoc signing was never the problem** — the same shape registers, launches as root and serves calls, measured on this machine after the label change — and during development, treat a label that has accumulated dead registrations as spent rather than debuggable. The only documented machine-wide reset is `sfltool resetbtm`, which clears **every** app's background items and is not a step to take casually.

The helper does **not** touch CA trust — see the HTTPS-trust entry for why that boundary is the surviving half of the 0.0.16 reasoning.
## What 0.0.16 deleted

**What 0.0.16 deleted, and what was wrong about the deletion.** `Engine/PrivilegedHelper` (the root daemon), the `HelperProtocol` module and the XPC half of `PrivilegedHelperClient` — ~1000 lines across two Tuist targets — were removed. They had been kept "as a design record" while never being loaded, never invoked and never exercised by CI, which is the worst of both: a reader has to establish it is dead before trusting anything near it, and the build paid for it every time. What actually needed keeping is *reasoning*, and that lives in the HTTPS-trust entry above and [ROADMAP § M2](../../ROADMAP.md#m2); `git log` has the code. Two consequences to know: `PrivilegedHelperClient` keeps its name while no longer wrapping any helper (renaming it would churn every `@Dependency` site and both test suites for a word), and `PrivilegedHelperClientTests` dropped from 23 tests to 17 — the six that went covered `SystemProxyParsing` / `ProxyServiceState` / `ProxyBackup`, all daemon-only. The seventh test in that file covered `SCDynamicStoreCopyProxies` key names on the *shipping* path and was kept, in `SystemProxySnapshotTests`.

**Deleting the code was right; the belief attached to it was not, and that is the transferable part.** "It could never load" was written from two refusals that had never been *run* — one was false and one was a string we had chosen ourselves — and because the entry read as settled physics rather than as an untested inference, it parked the feature for two releases and framed a Developer ID certificate as the only way out. Ten minutes with a throwaway `SMAppService` probe (two bundles, one ad-hoc, one signed with a free-account Apple Development identity) settled both. So: **a claim about what the platform refuses is a measurement, not a deduction** — when one of these entries is load-bearing enough to cancel a feature, the cheap probe is part of the cost of writing it down. The `git log` still has the deleted code, and the new helper is a clean rewrite rather than a revert, because the shape it needed (parameters not scripts, a derived requirement, no CA trust) is not the shape that was removed.
