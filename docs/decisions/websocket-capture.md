# WebSocket capture: three bugs, one of which crashed the app

> Moved out of `AGENTS.md` on 2026-08-07 (0.0.18), unedited. It is a **record**, not
> an instruction: what was tried, what it cost, and why the current shape is the
> shape. The invariants these produced live in [`AGENTS.md` § MCP Tools](../../AGENTS.md#mcp-tools), which links
> here — read that first; come here when you are about to re-open the question.

All three shipped in 0.0.16. The third one generalizes past WebSocket, and that is the
reason to keep the account rather than only the rule: `WebSocketFrameParser` is one of
the few places Loom parses **untrusted network bytes**, and the same three mistakes are
available to anything else that does.

**A `wss://` splice originates real upstream TLS, and an upgrade that fails is a flow like any other** — both took a fix (0.0.16). `WebSocketRelay` built its upstream `NIOSSLClientHandler` with `try?` and fell through to "no handler", which is not "no TLS attempted": it is plaintext written at a TLS server on a connection the client asked to be encrypted. The reachable instance was an **IP-literal origin** (`wss://192.168.1.10:8443/ws` — a LAN device, a dev server addressed by IP), because `NIOSSLClientHandler` rejects a literal as an SNI name; `SharedTLS.isIPLiteral` is now the one definition the relay and `NIOStreamingForwarder` both consult, and a handler that still won't build fails the *connect* rather than the confidentiality. Separately, the splice creates its capture sink only on success, so an upgrade that never reached its origin recorded nothing at all — the client got a fixed 502 and `get_recent_flows` stayed empty, which reads exactly like a client that never ran. `WebSocketRelay.fail` now logs it (`Log.ws`), records a failed `Flow`, and puts the reason in the 502 body: the § "log it for the human, return it for the agent" rule, applied to the one path that was exempt from it. **A third one crashed the app, and its shape generalizes: `WebSocketFrameParser` parses untrusted network bytes, so a trap there is never a valid answer.** A frame declaring the 64-bit extended length with its high bit set shifted into `Int`'s sign bit — Swift's `<<` *masks* rather than traps, which is why the overflow was invisible — and the resulting **negative** length sailed through `guard data.count >= index + length` before killing the process on `data[index ..< index + length]`, from a NIO event-loop thread, taking every other capture with it. Three rules now, each pinned by a test: lengths decode as `UInt64` and narrow to `Int` only once bounded (`maxFrameBytes`, 64 MiB — a frame is buffered whole before it is emitted, so an unbounded length is an unbounded allocation two wire bytes can ask for); every remaining-bytes check is a **subtraction** (`data.count - index >= n`), never an addition on a wire-supplied length; and "not enough bytes yet" and "these bytes aren't frames" are **different answers** (`Step.needMore` vs `.invalid`) — conflating them as `nil` is what made the parser keep trusting a desynchronised stream. On `.invalid` the tap stops parsing that direction *for good* (realignment from bytes alone is guesswork) while the splice keeps relaying every byte, and the reason reaches both audiences: `Log.ws` plus `Flow.webSocketCaptureError` → `get_flow_detail`'s `webSocket.captureStopped`, `captureTruncated` in the summary, and an orange note in the Inspector's frame log — because a frame log that silently stops growing is indistinguishable from a socket that went quiet.
